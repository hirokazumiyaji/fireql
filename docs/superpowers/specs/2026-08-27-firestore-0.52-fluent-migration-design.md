# Design: Firestore 0.52 Fluent API migration

**Date:** 2026-08-27  
**Status:** Approved (approach B1)  
**Goal:** Upgrade `firestore` from 0.51 to 0.52 and make Fluent API the only query/mutation entry point used by fireql.

## Background

firestore-rs 0.52 privatises the low-level `*Support` traits. Direct calls such as `db.query_doc`, `db.stream_query_doc_with_errors`, `db.create_obj`, and `db.aggregated_query_doc` no longer compile. The public entry point is `db.fluent()`.

fireql currently:

- Builds `FirestoreQueryParams` / `FirestoreAggregatedQueryParams` in `src/planner.rs`
- Executes via `FirestoreQuerySupport` / `FirestoreAggregatedQuerySupport` in executor modules
- Seeds emulator data via `FirestoreCreateSupport` / `FirestoreUpdateSupport` / `FirestoreGetByIdSupport` in `fireql-emulator-seed` and `tests/emulator.rs`

Batch writers and `firestore_document_from_map` remain public in 0.52 and stay as-is.

## Decision

**Approach B1 — PlannedQuery + Fluent execution**

- Introduce fireql-owned plan types instead of returning `FirestoreQueryParams`
- Build filters with `FirestoreQueryFilterBuilder` (`field().eq()`, `for_all`, `for_any`, …)
- Execute all reads/aggregations/seed upserts through `db.fluent()`
- Keep validation in planner; keep batch write path on the public batch writer API

Rejected alternatives:

- **Thin adapter (A):** Keep `FirestoreQueryParams` and only wrap execution — too shallow for a lasting 0.52 posture
- **B2 (filter-only Fluent):** Still centres on params structs
- **B3 (SQL→Fluent in executor):** Mixes validation and execution; hurts JOIN / aggregation clarity

## Architecture

```text
SQL AST (sql::*)
    │
    ▼
planner::plan_select / plan_aggregation
    │  validate_query_constraints
    │  build_filter via FirestoreQueryFilterBuilder
    ▼
PlannedSelect / PlannedAggregation   (fireql-owned)
    │
    ▼
executor::*  →  db.fluent().select() | .aggregate() | .insert() | .update()
    │
    ▼
Firestore results → FireqlOutput
```

## Plan types

```rust
pub struct PlannedSelect {
    pub collection_id: FirestoreQueryCollection,
    pub parent: Option<String>,
    pub all_descendants: bool,
    pub filter: Option<FirestoreQueryFilter>,
    pub order_by: Vec<FirestoreQueryOrder>,
    pub limit: Option<u32>,
    pub return_only_fields: Option<Vec<String>>,
}

pub struct PlannedAggregation {
    pub select: PlannedSelect, // order_by/limit empty; enforced in plan_aggregation
    pub aggregations: Vec<AggregationExpr>, // fireql SQL AST; Fluent mapping at execute time
}
```

Notes:

- `parent` is the absolute documents parent path when `collection('a/b/c')` is used (same resolution as today via `documents_path`)
- `all_descendants` is true for `collection_group(...)`
- Filters use firestore's public `FirestoreQueryFilter` model, but are **constructed only** via `FirestoreQueryFilterBuilder`
- Aggregations stay as fireql `AggregationExpr` until execute time, then map through Fluent aggregation builder
- `FirestoreQueryOrder` remains the firestore order model (small, used directly by Fluent `.order_by`)

### API rename

| Before | After |
|--------|--------|
| `build_query_params(...)` | `plan_select(...)` → `PlannedSelect` |
| `build_aggregated_query_params(...)` | `plan_aggregation(...)` → `PlannedAggregation` |
| `build_filter(expr, docs_path)` | `build_filter(fb, expr, docs_path)` using `FirestoreQueryFilterBuilder` |

`sql_value_to_firestore` / array helpers stay for UPDATE SET values and filter values.

## Filter construction (Fluent style)

`build_filter` recursively maps `FilterExpr` using the builder:

- Compare / IN / NOT IN / array_contains / array_contains_any / IS NULL → `fb.field(name).<op>(value)`
- AND → `fb.for_all([...])`
- OR → `fb.for_any([...])`

Nested AND/OR: build each child to `Option<FirestoreQueryFilter>`, then pass those options into `fb.for_all` / `fb.for_any` (firestore already treats `Option<FirestoreQueryFilter>` as `FirestoreQueryFilterExpr`). Do not manually construct `FirestoreQueryFilter::Composite { ... }` enums.

Validation (`validate_query_constraints`) is unchanged and still runs before filter build.

## Execution mapping

### SELECT (fields)

```rust
let mut q = db.fluent().select();
if let Some(fields) = planned.return_only_fields {
    q = q.fields(fields);
}
let mut q = q.from(planned.collection_id);
if let Some(parent) = planned.parent { q = q.parent(parent); }
if planned.all_descendants { q = q.all_descendants(); }
if let Some(filter) = planned.filter {
    q = q.filter(|_| Some(filter));
}
if !planned.order_by.is_empty() { q = q.order_by(planned.order_by); }
if let Some(limit) = planned.limit { q = q.limit(limit); }
q.stream_query_with_errors().await?
```

Same helper used for JOIN side queries, INSERT SELECT source, and UPDATE/DELETE document listing streams.

### SELECT (aggregations)

Build the select chain from `PlannedAggregation.select`, then execute via Fluent aggregate:

```rust
.aggregate(|agg| {
    // map each AggregationExpr → Fluent aggregation (count/sum/avg) with alias
    planned_aggregations_via_fluent(agg)
})
.query()
```

Aggregation construction uses the Fluent aggregation builder (`FirestoreAggregationBuilder`) for COUNT / SUM / AVG aliases—not hand-built `FirestoreAggregation` enums—so planner and executor stay on the Fluent surface.

### Batch UPDATE / DELETE

- Document ID stream: Fluent select as above (name/projection as today)
- Writes: existing `create_simple_batch_writer` + `firestore_document_from_map` (unchanged)

### Emulator seed + e2e fixtures

Replace Support-trait calls:

| Before | After |
|--------|--------|
| `create_obj` / `create_obj_at` | `db.fluent().insert().into(col).document_id(id)[.parent(p)].object(&data).execute()` |
| `update_obj` / `update_obj_at` | `db.fluent().update().in_col(col).document_id(id)[.parent(p)].object(&data).execute()` |
| `get_obj_*_if_exists` | `db.fluent().select().by_id_in(col)[.parent(p)].obj::<T>().one(id)` → `Option` |

Upsert logic in seed keeps exists-then-update/create behaviour using Fluent get + insert/update.

## Dependency

```toml
firestore = { version = "0.52", default-features = false, features = ["tls-webpki-roots"] }
```

No pin to 0.51 after this lands. MSRV remains whatever the repo/mise already requires (0.52 declares 1.90+).

## Testing

- Unit: planner tests assert on `PlannedSelect` fields / filter shape (update expectations that currently poke `FirestoreQueryParams`)
- Lib tests: existing coverage must pass
- Emulator e2e: existing `tests/emulator.rs` cases after Fluent seed migration
- Clippy: `-D warnings` clean

## Out of scope

- Firestore cache / listener APIs
- Rewriting batch writer to Fluent batch helpers (optional follow-up)
- Behavioural SQL changes
- Dependabot config changes beyond allowing 0.52

## Risks

| Risk | Mitigation |
|------|------------|
| Fluent `filter(|_| Some(owned_filter))` move/ownership friction | Build filter inside closure or clone when needed |
| Collection group / parent path mapping mismatch | Mirror current planner parent + `all_descendants` semantics; e2e covers group + subcollection |
| Aggregation Fluent builder alias differences | Keep operator construction close to current code; verify COUNT/SUM/AVG e2e |
| Large e2e seed churn | Small shared helpers in test/seed for insert/update/get |

## Success criteria

1. `firestore` dependency is 0.52 and the crate builds
2. No imports of `FirestoreQuerySupport`, `FirestoreAggregatedQuerySupport`, `FirestoreCreateSupport`, `FirestoreUpdateSupport`, or `FirestoreGetByIdSupport` in fireql sources/tests
3. No `build_query_params` / `db.query_doc` / `db.stream_query_doc*` / `db.create_obj*` call sites remain
4. `cargo test --lib` and emulator e2e (when emulator host set) pass
